# 完整归档与媒体压缩

用于跨月、长时间段或有较多媒体的导出。最终保留一个完整 Slinx ZIP，以及类似 WhatsApp 的根目录 `messages.jsonl + media/`；不生成 HTML。内部的分段采集、暂存、校验不是向用户交付的分包。

## 完整的含义与保存位置

- 完整表示指定范围内的消息、引用证据和可取得附件齐全；压缩副本不承诺与原文件逐字节相同。原始附件在独立目录保留，能从消息对应表追溯。原文、发送人和时间精度不因压缩改变。
- 每次导出使用 `~/Downloads/data/<会话>-<起止日期>-<唯一标记>/`，保留已有导出。交付根目录 `messages.jsonl`、一个完整 ZIP、本地 `media/`、必要的原件目录及 `export-report.json`。消息用相对路径关联媒体，不将媒体转成大段 base64 嵌入消息。
- ZIP 按既有格式仅包含根目录 `manifest.json`、`messages.jsonl`、`media/`。它包含完整消息和全部取得的附件副本；原始附件目录与报告放在 ZIP 外，避免重复放大上传体积。只给媒体路径、不把所需文件放进包里不算完整。
- 按 [转发内部消息与 RAG 追溯](forwarded-evidence.md) 将原始逐条记录和 `slinx_ref` 映射保存在根目录 JSONL，版本校验、缺失情况和续采进度保存在报告。取消独立 `evidence/` 数据文件和默认交接 Markdown。转发内部消息不只保留预览摘要，原作者、原时间、内部引用和附件归属分别核实；这些新字段不放进 ZIP 内的兼容消息。
- 来源不明、失效或本机未保存的附件仍记为缺失；不要把“已完成指定范围的采集”写成“每个原件均已找到”。

## 压缩顺序与质量边界

先核对来源与对应关系，再做无损整理和媒体副本压缩，最后实测整个 ZIP。没有统一压缩比例能保证所有图片细节和视频质量；以逐项验收为准，不承诺有损转换绝对无损。

| 内容 | 允许的处理 | 必须保留与核对 |
| --- | --- | --- |
| 消息、引用、时间、发送人 | 仅 ZIP 的无损压缩 | 不摘要、不翻译、不截断、不改变换行和表情；不以重复正文为理由删消息 |
| 普通照片 | 先尝试无损优化，再逐级试验质量或分辨率更小的副本 | 图片与消息一一对应，方向、宽高比、完整画面、可辨内容及色彩表现保持正确 |
| 带小字、尺寸、规格、报价、条码的图片，以及设计稿、关键颜色或纹理图 | 优先保留原图或无损优化；只有逐项确认关键信息未受影响才使用有损副本 | 核对最小文字、数字、标识和细节；无法核实就回退原件，不默认统一缩图 |
| 视频与动图 | 本地重新编码或无损优化；兼容性允许时视频优先 H.264/AAC MP4 | 完整内容、首尾、时长、方向、宽高比、原有音轨和关键动作；动图保留动画，不变成单张封面 |
| PDF、AI、PSD、Office、压缩文件及其他文档 | 保留原文件，使用 ZIP 无损压缩 | 原文件名和版本、实际字节、可打开性；不栅格化、不降成截图，不改设计结构、页数或嵌入内容 |

1. 原件只保存一次；未转换的原件可直接放在 `media/`，有压缩副本时将对应原件另存 `originals/`。同名文件使用独立安全路径，原名另存。同一批中只有 SHA-256 和字节内容都相同的附件才可共用一个媒体文件，所有消息的引用仍保留。画面相似、同名、不同分辨率的文件不自动合并。实际源消息去重与文件字节去重是两回事。
2. 图片使用确定性的本地编码工具优化，不能用生成式重绘、补画或 OCR 重建替换原图。不得裁剪、遮挡、水印覆盖或改色。处理方向信息后要保持显示方向一致；关键色彩所需的色彩配置不随意丢弃。每个转换图先检查解码、尺寸、比例与方向，再与原件对照可辨内容；关键文字和产品细节需放大核对。仅验证文件能打开不足以证明图片正确。
3. 视频先检查原分辨率、方向、总时长、音轨及内容用途。从原件逐级试编码，在画面可辨、声音可懂的前提下减小码率或分辨率；涉及小字、结构、动作或产品细节时提高质量或保留原件。不得为了尺寸预算截取片段、抽成几帧、静音、加速或改变播放时长。先核对完整解码和轨道，再抽查开头、中间、结尾及关键画面、声音。编码造成的极小容器/音频填充差异须与截断区分，不能以容差为名漏掉实际内容。
4. 每轮都从原件生成候选，避免反复压缩已损失的副本。选择通过验收且更小的版本；压缩后反而更大、关键细节模糊、色彩变化或声音异常时回退。达到质量边界后停止压缩，不为满足任意大小继续损坏内容。
5. 对每个采用的副本记录：对应消息 ID、原件相对路径与原名、原 SHA-256/字节数、副本路径/SHA-256/字节数、转换工具与参数、分辨率、视频时长和音轨核对结果、已完成的人工或视觉检查。将其写入 `export-report.json`，并在契约允许的 `provenance` 中注明为压缩副本；不能新增不受契约支持的角色或字段。原件角色名称若因现有契约用于媒体主项，也不代表副本是原始字节，必须在来源说明中澄清。

## 容量目标与接收端限制

以下是用户指定的导出目标，不代表 Slinx Talk 当前已支持这些容量，也不授权修改应用代码、数据库或部署。完整性和质量优先于压缩比例。

| 检查项 | 目标上限 | 计算口径 |
| --- | --- | --- |
| 完整 ZIP | 2 GiB，即 2,147,483,648 字节 | 最终单个 ZIP 文件的实际字节数，包含清单、消息、媒体及 ZIP 开销；不是附件大小之和 |
| 单个视频、图片或文件 | 512 MiB，即 536,870,912 字节 | 包内该附件解压后的实际字节数；采用压缩副本时按最终副本计算，不能用其在 ZIP 内的压缩占用代替 |

原件目录保存在 ZIP 外，不受副本的 512 MiB 目标约束；原件仍必须完整保存并可追溯。ZIP 的展开总大小另行统计，不假定它也小于 2 GiB。

1. 压缩前统计完整范围的消息、附件、原始总大小和最大附件，找出体积较大的媒体。按全包预算分配压缩力度，不用月份数量或短期样本估算替代最终验收。
2. 按本文件的质量要求压缩副本，目标为整包及每个附件均不超过表中上限。质量允许时为整包预留约 5% 软余量；不要为了余量牺牲关键文字、产品细节或视频内容。最终以实际文件字节数核对。
3. 在保证质量的前提下仍超过 2 GiB，或仍有单附件超过 512 MiB 时，继续保存并交付一个完整本地 ZIP、完整 JSONL/媒体目录和原件。明确标注“超过导出容量目标”，列出实际大小、超出的附件及原因；不声称达标，不拆包、不分卷、不删消息或附件、不截短视频、不依赖旧包的文件缩小包。文档即使在 ZIP 内压得很小，其解压后超过 512 MiB 也须单独报告，不能破坏文档结构来强行达标。
4. 接收端兼容性另行核对：读取实际部署已知限制，并检查本机 `backend/app/chat_import_policy.py`、`dev_chat_archive.py` 和 `dev_chat_contract.py` 中的上传大小、展开总大小、单文件大小、消息/附件数量和累计存储限制。已达到 2 GiB/512 MiB 目标的包仍可能超过接收端的较小限制，应报告“容量目标达标，但当前接收端不接受”。不能把用户的目标当作已上线能力，也不因现网限制更小而自动改成更低的压缩目标。
5. 不修改 Slinx Talk 的常量、数据库或部署，也不改写本地解析器上限来让校验通过。线上剩余额度无法核实时标“未核实”。ZIP、解包附件和记录都会占用导入存储，不能把 ZIP 体积直接当作累计配额用量。

在 `export-report.json` 中分别记录导出容量目标（字节）、实际 ZIP 大小、展开总大小、最大附件、每个超目标附件及其大小、目标是否达标、已核实的接收端限制和导入校验结果。目标达标和可导入是两个独立结论。

## 打包与校验

### 体积较小且满足导入限制时

按 SKILL.md 的命令使用 `scripts/finish.py`。它调用生产导入解析器，输出根目录原始 JSONL、ZIP、被引用的媒体/原件和报告，不再生成 HTML。它不负责自动压缩，且会把 ZIP 和附件读入内存。GiB 级归档即使满足接收端限制，也按下面的流式流程处理。保留脚本的正常校验，不用关闭校验或替换上限来冒充可导入。报告只代表所核对本地版本的格式结果，线上导入和剩余额度仍需另行确认。

调用前准备 Slinx 暂存清单/消息、必需的 `source-messages.jsonl`（v2 群头及逐条原始消息）、所需媒体、原件和报告。脚本将原始 JSONL 原样保存为输出根目录 `messages.jsonl`，检查父子关系、已匹配引用、每条 `slinx_ref` 和附件校验值；不替代人工或 UI 采集核实。它只复制已引用文件，原件、预览及证据路径均须列全，详见 [生成与验收](forwarded-evidence.md#生成与验收)。

### 大型归档或超过限制时

现有 `scripts/finish.py` 的入口会在导入超限时停止，且采用内存打包，不适合作为完整大归档的直接生成入口。按下列本地流程制作完整文件，不能因该脚本拒绝而停止归档或拆分交付：

1. 从已核对的统一原始数据生成最终清单和 Slinx 兼容消息；保留根目录原始 JSONL 和每条 `slinx_ref`。可复用 `finish.py` 的 `import_messages()`，其返回值为处理暂存引文后的 JSONL 字节；ZIP 中不含群头、`quoted_excerpt` 或内部层级字段。引用作者、原时间和引文在原始 JSONL 中分字段保存。
2. 使用标准流式 ZIP 写入完整的 `manifest.json`、`messages.jsonl` 和全部实际媒体，不把数个月视频一次性读进内存。用安全相对路径，拒绝越界路径及同一路径的不同内容；先写新临时文件，校验完成后再命名为正式交付文件，不覆盖原件。
3. 流式保存根目录原始 `messages.jsonl`（群头后逐条消息），复制其实际引用的媒体、原件及必要 UI 证据，并写报告。不生成 HTML，不依赖已删除的 `render()`。检查根目录原始记录与 ZIP 的对应关系，不通过省略旧记录缩小数据。
4. 依据既有契约检查字段和来源关系，对所有实体文件流式计算 SHA-256 与字节数，读取 ZIP 校验 CRC。单独列出体积、数量等接收端限制的超出项，不能把“超限”当成来源关系或文件完整性检查的通过。若结构本身不能满足当前导入契约，保存完整本地归档并如实列明差异，不声称它已经可导入。

### 两条路径共同核对

- 导出前后原始证据中的消息数量、消息 ID、发送人、正文、原始时间标签、顺序逐条对照。顶层与内部消息分别计数；Slinx 转发正文拼接是有映射的兼容呈现，不覆盖原始摘要或正文。媒体转换和必要的同包批次关联更新应可解释；不得出现未说明的内容变化、重复记录或缺漏。
- ZIP 中全部原生 `reply_to` 都能解析到正确顶层原消息；范围外、内部子消息或无法确定的来源保留已核实引文及根目录原始 JSONL 中的真实关系，不能指向内容近似的其他消息。引用正文不重复，原作者、原时间及引文分字段保留。
- 清单中的实际附件和 ZIP 内容、每条消息的媒体引用对应一致；所有完整附件的 SHA-256 和大小与最终字节一致。压缩前后的文件与所属消息逐一对应，不能串图或串视频。将真正缺失的项目与已保留的压缩副本区分。
- 根目录消息的来源键、父子关系、`slinx_ref`、ZIP 外层消息及附件 `slinx_path` 逐条互相对应。保存所有取得的媒体不等于所有内部归属已核实；`card_only`、未展开、缺失原文及未知时间分别报告。原始记录中的内部引用不能误当作 ZIP 原生顶层引用。
- 报告列出时间覆盖、采集截止点、完整性缺口、时间精度、各类数量、原件总大小、采用副本的总大小、ZIP 实际大小及展开大小、具体压缩与检查结果、导入障碍。正文检查、文件完整性、视觉检查和导入校验分别记结果；未做的检查标未核实。
